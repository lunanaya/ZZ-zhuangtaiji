2026-09-10，运行版本 v0.16.69。此文区分已验证的行为与建议方案，未将建议中的推测写进用户记忆。

## 本次实际操作

沿用酒馆现有 API，串行执行一次“读取上一轮正文”，没有清空状态或重新初始化。请求任务为 `PLAIN_MEMORY_SETTLE`，输入 7,080 字符，配置输出上限 9,000 tokens，约 14.1 秒完成。服务返回正常 stop，输出 603 字符、359 tokens。保存由 REV 4 更新到 REV 5，未报错。本次共 1 次付费模型请求，没有补发。

生成内容实际更新了日期、后院临水亭地图、两名在场人物的活动及灵隐寺日程。后台判断仍主要复述“确认行程、处理政务”，没有形成更具体的约束与可行性判断。

离线复算以当前“继续”为用户输入，使用已保存的注入设置，禁用独立世界书编译器部分：当前记忆共 35 条、约 1,362 字符，插件自身生成的正文注入为 943 字符。这不是完整酒馆请求大小，也不是 token 数。外部世界书、预设和历史聊天开销另计。

## 内容审查

| 项目 | 当前结果的问题 | 应怎样处理 |
|---|---|---|
| 行动范围 | 正文允许在书房小院活动但不许出院门；资源约束仍为“没有已生效的资源限制” | 抽取“对象、允许范围、边界、解除条件”。该条是直接事实提取遗漏，应优先修复，无需凭空推演 |
| 时间与日程 | “三日后”保留为相对短句，没有固定参照；时钟解析器不认识该年号日期 | 保存剧情时钟，日程首次建立时锚定。第十七日约定三日后，可算为第二十日；具体时辰不明确则保持未定。重读同一正文不能再往后顺延三天 |
| 场外人物 | 只有两名在场人物的活动。太后一党、亲王动向和职责没有可核对的行动前提 | 有来源的职责/行踪先提取；缺失时根据地点、能力、资源与已过时间推演范围，并标明推测。当前“极慢、禁止自动跳时”设置意味着场外活动也不应无故推进一大步 |
| 玩家任务与决策 | “彻底掌控夏寻樨”是另一角色的目标，却放在主角任务；“顺从安排”被概括成玩家目标 | NPC目标归人物或势力；玩家任务限于明确接受的事项。答应一次出行不能推导出永久顺从或放弃自由 |
| 关系与权限 | “绝不允许离开视线”与允许去院子里的具体指令存在张力 | 分开保存主观占有欲与实际许可。代码执行明确权限规则，不能把情感倾向直接当成物理禁令 |
| 触发条件 | “可能遭遇刺客/眼线”缺少实施者、准备状态、资源与触发依据 | 保留为未证实风险；先验证日期、到场、准备条件，再决定是否具备触发资格。不能因日程到期就自动生成袭击 |
| 知识边界 | “可能是前朝公主”属于不确定内容，知情名单却没有区分知道传闻和确认真相 | 分开“已确认、相信、怀疑、听说”，传播需渠道；场外推测不直接泄露给在场角色 |
| 世界进程 | “清除异己、彻底覆灭”过于抽象，缺少阶段和可判断条件 | 记录当前阶段、已满足条件、阻碍与下个检查点；有明确状态变化时推进，稳定时保持不动 |
| 旧记录 | 句子模式保存时没有基于剧情时钟的自动失效清理 | 补上生命周期规则；已过时的快照从活动记忆移除，重要结果留在本地历史，不能因“很久没提”删除规则或承诺 |

“还有内容可以推理”不等于所有空白都应补成事实。应先补正文已明确却漏掉的限制，再推断受前提约束的活动与风险，最后由代码判断条件是否成立。不能通过多制造事件来伪装推演深度。

## 代码层已确认的限制

- `src/storage.js` 的 `storyTimestamp` 仅识别数字公历形式；`resolveReminderTime` 仅覆盖今天、明天、后天等少量表达。实际年号日期及“三日后”的解析结果均为 null。
- `src/plain-memory.js` 的 `prepareSave` 维护轮次、提醒投递和少量时间缓存，但不清理已过期的句子。
- `missingModules` 以栏目是否有至少一条记录判断补齐。一个栏目已有内容，不代表人物覆盖、地点、条件与权限检查完整。
- 句子模式回传采用关键词、当前场景词和未来提醒筛选。它尚未执行任意自然语言条件、路径可达性、资源扣减或任务依赖判定。
- 后台 `planner.notes` 没有直接加入句子模式正文注入。当前“后台判断”即使列出结论，也不自动成为下一轮正文的约束；应将可靠结论归入相应状态，或建立经过本地校验的简短提示。
- 当前“未来”识别同时依赖栏目和部分关键词，不能稳定区分一条句子中的当前行动与未来安排。此次“批阅奏折，并确认三日后……”混在同一条活动里，是需要整理的实际例子。

## 建议的系统结构

保留现有卡片和 `module/text/before` 差量输出。代码在本地把短文本里少量约定标签编译成索引、时钟、条件、状态和依赖，不要求 AI 输出整套数据库或 UI 字段。

处理链路：正文事实提取与受限推演 → 本地校验 → 更新活动状态 → 清理失效项 → 选出当前场景相关内容 → 编译简短正文上下文。

代码适合负责：

1. 时间、相对日期锚定、到期与超期判断。
2. 明确数值的资源增减、上下限与重复结算保护。
3. 已结构化条件的 AND/OR、前置任务、到场条件、明确权限。
4. 地图已知路线、方向、耗时、开放规则；地图缺失不能判定为不连通。
5. 状态迁移与互斥：未开始、进行中、完成、取消、失效；同一人物的“当前活动”快照更新。
6. 索引、去重、投递预算、过期清理、回滚与防重复请求。

AI仍应负责：从自然语言抽取事实、解释含糊行为、判断人物动机、提出有依据的可能行动、理解开放剧情因果。代码只能验算已经明确表达的规则，不能把任意自然语言自动视为可执行条件。没有游戏规则依据时，不应凭空添加好感度、战力或成功概率。

## 过期清理应怎样做

| 记录类型 | 清理规则 | 必须保留什么 |
|---|---|---|
| 当前位置、当前活动 | 新的明确状态替换旧快照；移动进行中保留过程与目的地的区别 | 当前落点与仍在发生的行动 |
| 临时效果、临时权限 | 明确截止时间到达或解除条件成立时移出活动状态 | 若有后续影响，保留简短结果 |
| 日程 | 已完成/取消后移出活跃提醒 | 必要历史结果；到期未完成的日程应标超期，不能自动当成完成 |
| 任务、承诺 | 明确完成、取消或失效后退出活跃列表 | 完成结果、未兑现责任；没有提及不代表取消 |
| 触发器 | 一次性触发成功后消耗；前提被明确否定时失效 | 仍满足条件、尚未触发的项目 |
| 推测、风险 | 新事实否定时撤销；重新评估时不重复当成已发生事件 | 不确定性与成立条件 |
| 永久规则、身份、秘密 | 不按时间或热度自动删除 | 限定、例外、认知边界、关键历史 |

历史放在本地索引和快照中，正常正文不反复注入。回看某事时再按相关性召回。清理和归档不增加模型调用；对语义是否仍重要没有把握时，交给已有的一次更新请求判断。

## 更短的正文回传示例

下面是建议格式，不是本次已实现的输出。它展示如何保留当前必要信息并避免让正文 AI 重算规则：

```text
【当前】昭国四年秋第17日，淮州行馆书房。
【人物】夏以昼处理政务；夏寻樨在软榻看书。
【权限】夏寻樨可在书房及本院活动，暂不得出院门。
【关系】夏以昼有强烈占有欲；一次出行答应不等于永久顺从。
【日程】已约定第20日前往灵隐寺，时辰未定；当前不提前触发。
【写作边界】接续当前动作，不自动跳时、换场或替玩家决定；未证实风险不写成事实。
```

实际编译应只加入与本轮动作有关的项目；无需提醒的日程可完全不发。固定规则去重后按需保留，不能为了缩短而丢掉否定、例外或知识边界。比较收益应记录真实注入字符数及供应方返回的 token 用量，不承诺固定比例的“正文算力节省”。

## 优先级

第一批：剧情时钟与日期锚定、正文限制抽取、玩家/NPC目标分开、明确生命周期与安全清理。

第二批：条件编译器、任务依赖、地图通行与移动耗时验算；给无法解析的条件保留“需AI判断”，避免误触发。

第三批：角色动机与场外活动提案、势力资源与行动代价、知识传播渠道；每个提案须有前提与不确定性。

最后优化显示：倒计时、可行/受阻标记、阻碍原因、地点与关系图。显示应来自真实状态和校验结果，避免先填精美数值再寻找依据。

调用约束保持：首次初始化最多2次；正文后更新1次；手动智能整理1次；本地验算、清理、渲染和上下文编译0次。

本次完成实测和审查，未上线以上时钟、条件引擎或自动清理方案，也未把建议中的猜测批量写入用户状态。
